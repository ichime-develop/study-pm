# WBS生成品質評価

## 1. 目的

OpenAIモデル、プロンプト、Structured Outputsスキーマ、サーバー側生成戦略を変更したとき、どの実装がより良いWBSを生成するかを同じ条件で比較する。

「AIの文章品質」ではなく、ユーザーが利用できるWBS下書きとしての正確性、実行可能性、修正負荷を評価する。

## 2. 評価単位

- 評価入力は、固定した概要または目次テキスト、生成条件、評価用の期待学習範囲とする。
- 入力内容の解釈とWBS生成を一体として評価する。ユーザーに候補確認を求める中間画面は設けない。
- WBS生成戦略を比較するときは、同じ入力テキスト、生成条件、期待学習範囲を固定する。
- サーバー計画ロジックだけを比較するときは、AIの中間出力も固定する。
- 入力例、期待制約、評価結果を個人情報や著作物の全文を含めないfixtureとして管理する。

## 3. 評価データセット

次の代表ケースを含める。

| ケース | 主な検証 |
| --- | --- |
| 概要だけ | 限られた入力から実用的なWBSを作れるか |
| 短い目次 | 基本的な章・タスク分解 |
| 6ページ相当の目次 | 長文、複数階層、順序 |
| 10ページ相当の目次 | 入力上限付近、入力範囲の増加 |
| 複数教材 | 同名項目、重複、教材横断の整理 |
| 重点・軽め・除外あり | 優先度の反映 |
| 1日10ページ等のペース指定 | 数量条件と日程 |
| 解釈不能・単位混在のペース指定 | WBS生成前の確認要求 |
| 期限と学習時間が矛盾 | 警告、必要量、緩和案 |
| 1日プロジェクト | 日付境界 |
| 親なしタスクを含む計画 | 2階層制約内の表現 |

評価fixtureは実装時に版管理し、変更理由を記録する。

著作物の実目次を置き換えた8章構成の合成fixtureに加え、誤字、改行欠け、章表記混在、番号欠番・重複、3階層、4階層の合成fixtureを`backend/src/test/resources/fixtures/wbs-generation/`で管理する。`dataset-v2.json`を一覧と比較条件の正本とし、現行基準`prompt v4 / schema v1 / strategy v1`と候補`prompt v7 / schema v4 / strategy v3`を区別する。

## 4. 自動ハードゲート

次の1件でも失敗した生成結果は採用候補にしない。

- JSON Schema適合
- 必須項目充足
- temporaryKeyの一意性
- OpenAIアウトラインの一時キー一意性、親参照順序、非循環
- サーバー変換後WBS最大2階層
- 変換後PARENT/LEAFの保持項目
- 予定工数0.25時間単位
- 開始日 <= 終了日
- 親参照・入力元参照の存在
- 除外条件に該当する内容を含めない
- 入力元にないtemporaryKeyを参照しない
- サーバー検証を通過する
- 1日24時間を超える計画を生成しない
- 平日・土日と学習できない曜日から算出した通常配置上限、または期限優先の警告条件を満たす
- `PAGE`選択時はページ数量条件を満たす

## 5. 自動指標

### 5.1 学習範囲カバレッジ

```text
学習範囲カバレッジ =
  1件以上のLEAFで扱われた期待学習範囲数
  / fixtureで定義した除外以外の期待学習範囲数
```

100%を目標とする。同じ学習範囲を複数LEAFへ分けることは許可するため、単純な1対1一致は要求しない。期待学習範囲は品質評価だけに用いるfixture上の注釈であり、プロダクトの永続データやユーザー確認対象にはしない。

### 5.2 対応関係

- 存在しない入力元temporaryKey参照数
- 入力元対応がないLEAF数
- 除外条件に反するLEAF数
- 同じtask temporaryKeyの重複数

### 5.3 条件違反

- プロジェクト期間外の日数・タスク数
- 希望学習時間の超過工数
- 学習できない曜日へ配置した工数
- 平日・土日の学習可能時間を超えた日数・工数
- ペース指定違反数
- 期限優先時の警告欠落数
- ユーザー入力の数量条件から算出した必要日数との不一致数

計画警告として許可した超過と、仕様違反を区別して集計する。

### 5.4 安定性

同一入力を複数回生成し、次を記録する。

- ハードゲート通過率
- 学習範囲カバレッジの分散
- 総予定工数の分散
- 親タスク数・LEAF数の分散
- 構造再生成率
- ユーザー再試行が必要になった率

## 6. 人手評価

各項目を1〜5で評価し、根拠を短く記録する。

| 観点 | 1 | 3 | 5 |
| --- | --- | --- | --- |
| タスク粒度 | 大きすぎる・細かすぎる | 一部修正が必要 | 実行・進捗更新しやすい |
| 親タスクのまとめ方 | 意味のない分類 | 概ね妥当 | 学習順序と内容が明確 |
| 工数配分 | 明らかに不自然 | 一部調整が必要 | 優先度と内容に対して妥当 |
| 日程実現性 | 実行困難 | 警告込みで調整可能 | 条件内で実行可能 |
| 学習順序 | 前提関係が崩れる | 一部入替が必要 | 自然な前提順序 |

「重点範囲の平均工数が通常範囲より長い」などの単純な大小関係は自動品質指標にしない。入力範囲の粒度やLEAF分割数に左右され、誤った最適化を招くためである。

## 7. 修正負荷

AI03の下書き編集・変換が実装された後に次を測る。

- 変換までに編集したタスク数
- 追加・削除したタスク数
- 親変更数
- 日付・工数変更数
- 再生成回数
- 下書き表示から変換までの時間

初期のモデル・プロンプト選定では修正UIが未実装のため、修正負荷を必須指標にしない。

## 8. 性能と費用

- OCR画像数
- AI入力・出力トークン数
- WBS生成時間
- 総処理時間
- 外部サービス呼び出し回数
- 再試行回数
- 1生成あたり概算費用

入力本文を評価ログへ保存しない。fixture IDと版情報で追跡する。

## 9. 版管理

各結果に次を記録する。

- datasetVersion
- modelName
- promptVersion
- schemaVersion
- strategyVersion
- applicationCommit
- 実行日時

各fixtureは原則1回実行し、`riskLevel = HIGH`のfixtureだけ追加で2回実行する。実API未実行の結果を成功として記録せず、未測定として明示する。

dataset v2の実API評価は、APIキーを環境変数へ設定した上で、明示的に次を実行する。通常の`test`や`verify`では外部APIを呼び出さない。

```bash
RUN_OPENAI_WBS_EVALUATION=true \
  ./mvnw -f backend/pom.xml -Dtest=OpenAiWbsGenerationEvaluationTest test
```

結果は`backend/target/wbs-generation-evaluation-v2-result.json`へ出力する。各実行には構造通過、カバレッジ、親・LEAF数、総工数、構造再生成有無、入出力トークン数を記録し、全体には構造通過率と構造再生成率を記録する。構造ゲートに失敗した実行がある場合は、結果を書き出した後にテストを失敗させる。

どれかを変更した比較結果を別版として扱う。

## 10. 採用判断

初期段階では、異なる性質の指標を1つの総合点へまとめない。

1. ハードゲートをすべて通過する。
2. 学習範囲カバレッジと条件違反が同等以上である。
3. 人手評価の中央値が高い。
4. 同等品質なら、安定性、処理時間、費用が良い案を採用する。

採用理由と、却下案に対する改善点を評価記録へ残す。実装後の修正負荷が高い場合は、モデルだけでなく入力解釈、プロンプト、サーバー計画ロジックを個別に見直す。

## 11. 反復サイクル

```text
固定fixtureを選ぶ
  -> 現行版を複数回生成
  -> 自動ゲート・指標を集計
  -> 人手評価
  -> 変更対象を1つに絞る
  -> 再評価
  -> 採用判断
  -> 設計書と版を更新
```

一度にモデル、プロンプト、スキーマ、サーバーロジックをすべて変えない。因果を比較できる単位で変更する。
