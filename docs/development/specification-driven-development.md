# 仕様駆動開発

## 目的

`study-pm` の開発では、開発者の学習目的として仕様駆動開発の考え方を取り入れる。

仕様駆動開発は、最終MVPのアプリ機能には含めない。

## 基本方針

1. 要件定義で、ユーザーへ提供する振る舞いを明確にする。
2. 基本設計で、画面、API、データ、主要な業務ロジックを整理する。
3. 実装前に、未決事項と判断理由を明確にする。
4. 実装後は、要件・設計との差分をレビューする。

## MVP3の反復的な進め方

AIを利用するMVP3では、同じ入力でも生成結果が変わり得るため、詳細設計を一度で固定してから全実装を完了する進め方だけに依存しない。ただし、要件と安全上の不変条件は先に固定する。

### 先に固定するもの

- 外部サービスへの送信範囲
- AI出力を直接Project/WBSへ保存しないこと
- ユーザー確認、所有者制御、WBS階層、工数単位
- 停止・期限・再試行・利用上限
- プロジェクト変換時の再検証とトランザクション

### 反復して選定するもの

- OpenAIモデル
- プロンプト
- Structured Outputsスキーマの詳細
- 入力内容の解釈とWBS生成のサーバー戦略
- timeout、deadline、再試行、保持期間、生成上限の具体値

### 開発サイクル

1. 小さい縦スライスを設計する。
2. 固定fixtureで実装・検証する。
3. `wbs-generation-evaluation.md` の指標で評価する。
4. 変更対象を1つに絞って改善する。
5. 採用した判断を要件・基本設計・詳細設計へ同期する。
6. 次の縦スライスへ進む。

技術検証だけを独立した使い捨てフェーズにせず、実装可能な最小機能を作成して評価し、採用したコードと設計を積み上げる。

## 成果物とAI指示ファイルの違い

| 種別 | 例 | 役割 |
| --- | --- | --- |
| 成果物 | 要件定義、基本設計、レビュー記録 | 人間が確認し、プロジェクトの判断根拠として残す |
| AI指示ファイル | Skill、AGENTS.md | AIに作業させるためのルールや出力形式を定義する |

## 現時点で作る成果物

- 要件定義
- 要件定義レビュー
- 基本設計
- 必要になった領域の詳細設計
- 基本設計レビュー

## 必要になった時点で追加する成果物

- 詳細設計
- テスト仕様書

詳細設計は、基本設計だけでは実装判断が不足する領域に限定して追加する。
