## 2. 背景

私が、Java, SQL, ITアーキテクト, プロジェクト管理について、一度に学びたいと考え、
本アプリを作ることになった。

一方、一般的にあらゆる勉強する人たちの課題として、教材や目標を決めても、学習範囲の分解、予定と実績の比較、遅延の把握、疑問点の管理が別々になりやすいということがある。

本アプリは、学習目標を「学習プロジェクト」として管理できるツールを作りたい。
特にターゲットをシステムエンジニアとする。
エンジニアが自分の勉強しながら管理についても学べるようにしたい。
そのため、学習内容をWBSに分解して、予定工数、実績工数、進捗率を継続的に記録できるようにする。
さらに、EVMやバーンダウンチャートにより、学習の進み具合と計画との差を可視化する。

## 3. アプリの目的

1. 学習目標をプロジェクト単位で明確にする。
2. 学習内容をWBSとして分解し、実行可能なタスクにする。
3. 予定工数、実績工数、進捗率を記録し、計画との差を把握する。
4. EVMとバーンダウンチャートにより、遅延や工数超過を早期に発見する。
5. 学習中の疑問と回答を蓄積し、後から振り返れるようにする。
6. Java、SQL、設計を実践的に学べる開発題材とする。

## 4. 想定ユーザー

### 4.1 主なユーザー

- Java、SQL, クラウド系などの資格試験などを学習するエンジニア
- 独学の計画と進捗を定量的に管理したい人
- 学習中の疑問と回答を一元管理したい人

### 4.2 利用形態

- 初期リリースでは、各ユーザーが自分の学習情報のみを管理する。
- チーム学習、講師によるレビュー、他ユーザーへの公開は対象外とする。

## 5. 用語定義

| 用語 | 定義 |
| --- | --- |
| 学習プロジェクト | 学習目標、期間、計画工数をまとめる管理単位。例: Java Silver合格、SQL基礎習得、設計書入門1冊読破、PINBOKの内容理解|
| WBS | 学習内容を階層的に分解したタスク構造 |
| WBSタスク | 学習する具体的な作業。例: 第1章を読む、演習問題を解く |
| 予定工数 | タスク完了に必要と見積もった時間 |
| 実績工数 | 実際に学習した時間 |
| 進捗率 | タスクの完了度を0%から100%で表した値 |
| 学習記録 | ある日に実施した学習時間とメモ |
| 質問 | 学習中に発生した疑問点 |
| BAC | Budget at Completion。プロジェクト全体の予定工数 |
| PV | Planned Value。基準日時点で完了予定だった作業の予定工数 |
| EV | Earned Value。進捗率に応じて完了したとみなす予定工数 |
| AC | Actual Cost。本アプリでは実績工数 |
| SPI | Schedule Performance Index。スケジュール効率を表す指標 |
| CPI | Cost Performance Index。本アプリでは工数効率を表す指標 |
| バーンダウンチャート | 日ごとの残予定工数を表示するグラフ |

## 6. 基本方針

### 6.1 MVPの考え方

初期リリースでは、学習計画を手動で登録し、日々の学習実績を入力して、進捗を可視化する基本サイクルを完成させる。

```text
学習プロジェクト作成
  -> WBS作成
  -> 学習予定の設定
  -> 学習記録の登録
  -> 進捗率の更新
  -> ダッシュボードで状況確認
  -> 質問と回答メモの蓄積
```

### 6.2 MVPでの前提

- Webブラウザから利用する。
- ユーザーはメールアドレスとパスワードでログインする。
- 1つのWBSタスクは1つの学習プロジェクトに所属する。
- WBSは複数階層を持てる。
- 工数の単位は「時間」とし、0.25時間単位で入力できる。
- 進捗率はユーザーが手動で更新する。
- 実績工数は学習記録から自動集計する。
- 登録した質問に対するAI回答を生成し、回答メモとともに保存できる。

## 9. 業務ルール

### 9.1 プロジェクト状態

| 状態 | 条件・用途 |
| --- | --- |
| 未着手 | 学習開始前のプロジェクト |
| 進行中 | 学習を実施しているプロジェクト |
| 完了 | 目標を達成したプロジェクト |
| アーカイブ | 通常の一覧から除外するプロジェクト |

### 9.2 WBSタスク状態

| 状態 | 条件・用途 |
| --- | --- |
| 未着手 | 進捗率が0%のタスク |
| 進行中 | 進捗率が1%以上99%以下のタスク |
| 完了 | 進捗率が100%のタスク |

タスク状態は進捗率から自動判定する。状態と進捗率を別々に更新させない。

### 9.3 WBS階層と集計

- 子タスクを持たないタスクを「リーフタスク」とする。
- 予定工数、予定日、進捗率は原則としてリーフタスクに入力する。
- 親タスクの予定工数は、直下または配下のリーフタスクの予定工数合計とする。
- 親タスクの実績工数は、配下のリーフタスクに登録された学習記録の合計とする。
- 親タスクの進捗率は、配下のリーフタスクの予定工数を重みとした加重平均とする。
- 親タスクに子タスクを追加した後は、親タスクへ学習記録を直接登録しない。
- 循環参照となる親子関係は登録できない。
- WBS階層の上限はMVPでは5階層とする。

### 9.4 進捗率

- リーフタスクの進捗率はユーザーが手動で入力する。
- 入力可能な値は0%から100%とする。
- MVPでは10%単位での入力を基本とする。
- 実績工数を登録しても、進捗率は自動では増加しない。
- 完了済みタスクの進捗率は100%とする。
- 進捗率を更新した場合、システムは変更後の値を進捗履歴として保存する。

### 9.5 工数

- 工数の表示単位は時間とする。
- 工数は小数で保持し、0.25時間単位で入力できる。
- プロジェクトの予定工数は、配下のリーフタスクの予定工数合計とする。
- プロジェクトの実績工数は、配下の学習記録の学習時間合計とする。

### 9.6 遅延判定

以下を満たすWBSタスクを遅延として扱う。

```text
基準日 > 終了予定日
かつ
進捗率 < 100%
```

### 9.7 EVM計算ルール

EVMは金額ではなく学習時間を単位として扱う。

| 指標 | 計算式 | 意味 |
| --- | --- | --- |
| BAC | 全リーフタスクの予定工数合計 | プロジェクト全体の予定工数 |
| PV | 基準日までに完了予定の作業量 | 計画上、基準日までに消化する予定工数 |
| EV | 予定工数 × 進捗率の合計 | 実際に完了したとみなす作業量 |
| AC | 基準日までの学習記録の学習時間合計 | 実際に使用した工数 |
| SV | EV - PV | 正なら計画より進んでいる |
| CV | EV - AC | 正なら予定工数より効率が良い |
| SPI | EV / PV | 1以上なら計画以上の進捗 |
| CPI | EV / AC | 1以上なら予定工数以内の効率 |

PVは、各リーフタスクの予定工数を開始予定日から終了予定日までの日数で均等配分して算出する。開始予定日と終了予定日が同日の場合、その日に予定工数の全量を計上する。

PVまたはACが0の場合、SPIまたはCPIはゼロ除算を避けて「算出不可」と表示する。

### 9.8 バーンダウン計算ルール

- 縦軸は残予定工数、横軸は日付とする。
- 理想線は、プロジェクト開始日のBACから目標終了日の0まで直線で減少させる。
- 実績線は、日ごとのEVをBACから差し引いた値とする。
- 残予定工数は0未満にしない。

## 10. 非機能要件

### 10.1 性能

| ID | 要件 |
| --- | --- |
| NFR-PERF-01 | 通常の画面表示は、一般的な利用状況で3秒以内を目標とする。 |
| NFR-PERF-02 | 一覧検索は、1ユーザーあたりプロジェクト100件、WBSタスク10,000件、学習記録50,000件を想定して実用的な速度で動作する。 |
| NFR-PERF-03 | 集計処理に必要な検索条件には適切なインデックスを設定する。 |

### 10.2 セキュリティ

| ID | 要件 |
| --- | --- |
| NFR-SEC-01 | 認証済みユーザーのみアプリの主要機能を利用できる。 |
| NFR-SEC-02 | ユーザーは他ユーザーのデータを閲覧・更新できない。 |
| NFR-SEC-03 | パスワードは安全なハッシュ方式で保存する。 |
| NFR-SEC-04 | 入力値検証をサーバー側でも行う。 |
| NFR-SEC-05 | SQLインジェクション、XSS、CSRFへの対策を行う。 |
| NFR-SEC-06 | 秘密情報や認証情報をログに出力しない。 |
| NFR-SEC-07 | AIサービスへ送信する情報に、不要な個人情報や秘密情報を含めない。 |

### 10.3 可用性・バックアップ

| ID | 要件 |
| --- | --- |
| NFR-AVL-01 | 個人学習用途として、計画停止を除き継続利用できることを目標とする。 |
| NFR-AVL-02 | データベースを定期的にバックアップできる構成とする。 |
| NFR-AVL-03 | 障害時に原因を調査できるログを記録する。 |

### 10.4 保守性・拡張性

| ID | 要件 |
| --- | --- |
| NFR-MNT-01 | Webフロントエンドとバックエンドの責務を分離する。 |
| NFR-MNT-02 | 将来のFlutterアプリから利用できるREST APIとしてバックエンド機能を提供する。 |
| NFR-MNT-03 | Google認証を追加できるよう、ユーザー認証方式を拡張可能にする。 |

### 11.1 データ保持方針

- プロジェクトはアーカイブによる非表示を基本とする。
- 学習記録の変更後は、実績工数の集計結果との整合性を保つ。
- 外部サービス固有の情報を主要業務データへ直接埋め込みすぎない。

## 14. MVPの受入条件

以下を満たした場合、MVPの主要要件を満たしたと判断する。

1. ユーザーがアカウントを作成し、ログインできる。
2. ユーザーが学習プロジェクトを作成できる。
3. ユーザーがプロジェクト内に複数階層のWBSを作成できる。
4. ユーザーがWBSタスクに予定日、予定工数、進捗率を設定できる。
5. ユーザーがWBSタスクに対して学習記録を登録できる。
6. 学習記録からタスクとプロジェクトの実績工数が正しく集計される。
7. 親タスクとプロジェクトの進捗率が、予定工数による加重平均で正しく集計される。
8. プロジェクト詳細でBAC、PV、EV、AC、SPI、CPIを確認できる。
9. プロジェクト詳細でバーンダウンチャートを確認できる。
10. 遅延しているタスクを確認できる。
11. ユーザーが質問と回答メモを登録し、未解決・解決済みを管理できる。
12. ユーザーが登録した質問に対するAI回答を生成・保存できる。
13. ユーザーがAI回答と回答メモを区別して確認できる。
14. ユーザーが他ユーザーのデータを閲覧・更新できない。

## 15. 制約・前提事項

- 初期リリースは個人開発として、機能を絞って完成を優先する。
- PCブラウザでの利用を主対象とする。
- 日本語UIを主対象とする。
- タイムゾーンはユーザー設定を導入するまで日本標準時（JST）を基準とする。
- 日付は日単位で管理し、MVPではタスクの開始時刻・終了時刻を管理しない。
- EVMは学習時間をコストとして扱うため、一般的な金額ベースのEVMとは表示上の意味が異なる。
- AI回答は誤りを含む可能性があるため、参考情報として表示し、ユーザーが回答メモで検証結果を残せるようにする。
