# UIモック

## 1. 目的

UIモックは、要件定義の内容が実際の画面として成立するかを確認するために作成する。

本モックの目的は、見た目の完成度よりも、次の観点を検証することである。

- ユーザーが迷わず主要操作を進められるか
- 要件で定義した入力項目が画面に置けるか
- WBS、EVM、質問管理などの複雑な情報が理解しやすいか
- 画面を見たときに要件の不足や矛盾を発見できるか

## 2. 方針

| 項目 | 方針 |
| --- | --- |
| PC Webモック | React + TypeScript + Vite |
| スマホアプリ | 別リポジトリ `study-pm-mobile` で作成する想定 |
| データ | 固定のダミーデータ |
| API接続 | しない |
| DB接続 | しない |
| 認証処理 | しない |
| 保存処理 | 原則として永続化しない |
| 対象 | PC Web版の最終MVP主要機能を確認する |

このリポジトリでは、PC Web版の画面を優先して確認する。

将来のFlutterスマホアプリでは同じ主要機能を別UIで提供する想定だが、スマホアプリの画面モックと実装は `study-pm-mobile` 側で扱う。

このリポジトリでは、将来のスマホアプリからも利用できるAPI、認証、データ、入力制約、計算ルールを意識して設計する。

## 3. モックで確認すること

- ダッシュボードで、今日やること、遅延、直近の学習記録が把握できるか
- プロジェクト一覧で、状態、進捗、予定工数、実績工数が見やすいか
- プロジェクト詳細で、WBS、集計値、学習記録への導線が分かりやすいか
- WBS編集で、親タスクとリーフタスクの違いが分かるか
- 学習記録登録が少ない操作でできるか
- AI学習計画生成の結果確認やWBS編集がPC Webで成立するか

## 4. モックで扱わないこと

- 実際のログイン処理
- API設計
- DB設計
- AI API連携
- 本番向けの状態管理
- 詳細なエラーハンドリング実装

## 6. フィードバック方法

UIモックを確認して見つかった要件の不足や矛盾は、次のいずれかに反映する。

- 要件定義書の修正
- 画面要件の追加
- 基本設計で検討する事項への追加
