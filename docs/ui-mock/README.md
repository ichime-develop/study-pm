# UIモック

## 1. 目的

UIモックは、要件定義の内容が実際の画面として成立するかを確認するために作成する。

本モックの目的は、見た目の完成度よりも、次の観点を検証することである。

- ユーザーが迷わず主要操作を進められるか
- 要件で定義した入力項目が画面に置けるか
- WBS、EVM、AI学習計画生成などの複雑な情報が理解しやすいか
- 画面を見たときに要件の不足や矛盾を発見できるか

## 2. 方針

| 項目 | 方針 |
| --- | --- |
| PC Webモック | React + TypeScript + Vite |
| スマホアプリ | 別リポジトリ `study-pm-mobile` で作成する想定 |
| データ | 固定のダミーデータ |
| API接続 | しない |
| DB接続 | しない |
| 認証処理 | しない |
| 保存処理 | 原則として永続化しない |
| 対象 | PC Web版の最終MVP主要機能を確認する |

このリポジトリでは、PC Web版の画面を優先して確認する。

将来のFlutterスマホアプリでは同じ主要機能を別UIで提供する想定だが、スマホアプリの画面モックと実装は `study-pm-mobile` 側で扱う。

このリポジトリでは、将来のスマホアプリからも利用できるAPI、認証、データ、入力制約、計算ルールを意識して設計する。

## 3. 画面レイアウト方針

PC Web版のモックでは、画面間の横幅差で印象や情報量が変わらないよう、メインコンテンツ幅を揃える。

| 項目 | 方針 |
| --- | --- |
| メインコンテンツ最大幅 | 1280pxを標準とする |
| 配置 | メインコンテンツは中央寄せにする |
| WBS・ガント | 他画面と同じメイン幅を使い、表内部の横長情報は横スクロールで扱う |
| 一覧・フォーム・分析 | WBSと同じメイン幅を使い、必要に応じて列やカードを折り返す |
| サイドバー | UIモックでは画面切り替え・要件検証用に表示する。本実装では常設サイドバーを前提にしない |

### 3.1 一覧UIの方針

プロジェクト一覧、未完了タスク、学習記録、計画案WBSなどの一覧は、同じ操作感と列配置に揃える。

| 項目 | 方針 |
| --- | --- |
| 行クリック | 行全体を押せる一覧は `button` として扱う |
| 主列 | プロジェクト名、タスク名、メモなどの主情報は左寄せにする |
| 状態・日付・数値 | 状態、期間、終了予定、進捗、工数は中央寄せにする |
| 操作列 | 操作列は必要な場合だけ置く。行全体で編集できる場合は「編集」列を置かない |
| 親行・グループ行 | 成功色ではなくニュートラル背景で区別する |
| hover / focus | クリック可能な行は同じhover/focus表現にする |
| selected | 編集パネルなどで選択中の行は淡い主色背景で示す |
| 空状態 | データがない場合はヘッダーを出さず、空状態メッセージを表示する |

## 4. モックで確認すること

- プロジェクト一覧で、状態、進捗、予定工数、実績工数が見やすいか
- プロジェクト概要で、主要指標・警告・未完了タスクから次の行動を判断できるか
- プロジェクト内ナビゲーションで、状態を確認・変更し、WBS・学習記録・進捗分析へ自然に切り替えられるか
- WBS編集で、親タスクとリーフタスクの違いが分かるか
- 学習記録登録が少ない操作でできるか
- AI学習計画生成の結果確認やWBS編集がPC Webで成立するか

## 5. モックで扱わないこと

- 実際のログイン処理
- API設計
- DB設計
- AI API連携
- 本番向けの状態管理
- 詳細なエラーハンドリング実装

## 7. フィードバック方法

UIモックを確認して見つかった要件の不足や矛盾は、次のいずれかに反映する。

- 要件定義書の修正
- 画面要件の追加
- 基本設計で検討する事項への追加
