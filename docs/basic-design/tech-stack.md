# 技術スタック

## 1. 目的

要件レビューで基本設計へ移管された技術選定事項（DSG-TBD-01〜03）を決定する。

- DSG-TBD-01: PC Webフロントエンドの構成と採用技術
- DSG-TBD-02: バックエンドの構成と採用技術
- DSG-TBD-03: データベース製品

## 2. 前提条件

- 個人開発・1人運用を前提とし、運用コストと学習コストを重視する。
- REST APIは将来のFlutterスマホアプリ（別リポジトリ `study-pm-mobile`）からも利用する（17.1）。フロントエンドとバックエンドの分離が要件で決まっている。
- 進捗履歴・WBS計画履歴・プロジェクト期間履歴など、リレーショナルな集計処理が中心となる。
- 認証はメールアドレス・パスワードのみ（MVP1）。
- AI学習計画生成（OCR・AI連携）はMVP3。
- UIモック（`mock/`）はReact 19 + TypeScript + Vite 7で作成済み。本実装ではUI仕様・実装参考として移植し、固定データや要件検証用サイドバーは持ち込まない。

## 3. 採用スタック

| 領域 | 採用 | バージョン方針・補足 |
| --- | --- | --- |
| フロントエンド | React + TypeScript | React 19。UIモックと同一系統とし、移植コストを抑える |
| ビルド | Vite | Vite 7。Node.js 20.19+ / 22.12+ が必要。ローカル環境はv25で充足 |
| ルーティング | React Router | `/projects/:id/wbs` など、画面遷移図に沿ったURL設計に使う。Data Routerは必須にせず、データ取得はTanStack Queryへ寄せる |
| サーバー状態管理 | TanStack Query | APIデータの取得、キャッシュ、再取得を担当する。Reduxは採用しない |
| ローカル状態管理 | React標準（`useState`等） | WBS編集などの画面内一時状態はReact標準で扱う |
| UI | 独自CSS | UIモックで確立したデザインルールを継承する。UIライブラリは採用しない |
| バックエンド | Java 21 LTS + Spring Boot 3.x | Spring Bootは3.xの最新安定版を実装開始時に固定する。Spring Web / Spring Security / Spring Data JPAを利用する |
| API仕様 | springdoc-openapi | OpenAPIを自動生成する。将来Flutterアプリが同じAPIを利用する前提のため必須とする |
| DB | PostgreSQL 17 | AWS利用を見据え、実績と安定性を重視する。PostgreSQL 18固有機能は本用途では不要 |
| マイグレーション | Flyway | DBスキーマ変更を履歴管理する |
| ORM | Spring Data JPA | 基本CRUDと関連取得を担当する。EVM集計など複雑なクエリのみSQLで補う |
| テスト（バックエンド） | JUnit 5 + Testcontainers | 集計・履歴ロジックは本物のPostgreSQLで検証する |
| テスト（フロントエンド） | Vitest + Testing Library | 画面コンポーネントとユーザー操作単位のテストに使う |
| ローカル開発環境 | Docker Compose（PostgreSQL）+ Vite dev server | バックエンドはローカルJVM、DBはDocker Composeで起動する |

## 4. 検討した代替案

| 案 | 構成 | 却下理由 |
| --- | --- | --- |
| Next.js フルスタック | Next.js + API Routes + Prisma + PostgreSQL | TypeScript単一言語で開発速度は最速だが、Javaで実装するという方針と合わない。API RoutesはFlutterからも使う独立REST APIとしてはやや設計が曖昧になりやすい |
| Kotlin + Spring Boot | React + Kotlin + Spring Boot + PostgreSQL | 書き味は良いが、Javaで実装するという当初方針から外れる |

## 5. リポジトリ構成

### 5.1 方針

現時点ではAI活用（Claude Code等による横断編集）のしやすさを優先し、フロントエンドとバックエンドを1つのリポジトリ（モノレポ）にまとめる。

```
study-pm/
├── docs/
├── frontend/        (React + TypeScript + Vite。mock/ のUI仕様を参考に本実装へ移植)
├── backend/         (Java + Spring Boot)
└── ...
```

Flutterスマホアプリは既存方針どおり別リポジトリ `study-pm-mobile` とする。バックエンドは最初から独立したREST APIとして設計するため、Webフロントエンドと同一リポジトリに置くかどうかはFlutter対応に影響しない。

### 5.2 モノレポを選ぶ理由

- 1つのAIセッションでフロントエンド・バックエンド双方を横断して読み書きできる（例: APIのレスポンス変更とフロントの型定義変更を同時に行う）。
- 個人開発・基本設計〜開発初期のフェーズでは、リポジトリ分割によるデプロイ・権限分離のメリットよりも、AIでの開発効率を優先する。

### 5.3 リポジトリ分割の再検討タイミング

次のいずれかが発生した時点で、リポジトリ分割を再検討する。

- AWS等のデプロイ先が確定し、CI/CDパイプラインを構築するとき（フロントエンドとバックエンドでデプロイ先・デプロイ方式が異なる場合、パイプラインの都合上リポジトリを分けた方が素直になることがある）。
- 開発チームに2人目以降が加わり、権限分離やレビュー担当の切り分けが必要になったとき。
- フロントエンドとバックエンドのリリースサイクルが明確にズレ始めたとき。

### 5.4 分割・統合の可逆性

モノレポとリポジトリ分割は、Gitの標準機能内でどちらの方向にも履歴を保ったまま移行できる。今回の選択が将来を縛らないことを確認済み。

- **分割する場合**: `git filter-repo` や `git subtree split` で、対象ディレクトリのコミット履歴を保持したまま新しいリポジトリへ切り出す。
- **統合する場合**: `git subtree add` や `git remote add` + `merge --allow-unrelated-histories` で、別リポジトリの履歴を保持したままモノレポへ取り込む。

## 6. 保留事項

| 事項 | 方針 | 決定時期 |
| --- | --- | --- |
| 認証方式 | JWTを有力候補とする。Flutter共用APIを前提にするとセッションより扱いやすいが、失効管理の設計コストを確認してから確定する | API設計の冒頭 |
| デプロイ先 | AWS想定。料金、運用負荷、バックアップ方式を見て判断する | インフラ構成検討時。DSG-TBD-07（バックアップ方式）も合わせて決定する |
| OCR・AI学習計画生成に利用するサービスとモデル（DSG-TBD-04） | MVP1・MVP2では扱わない | MVP3着手時 |
| AI学習計画生成のタイムアウト値（DSG-TBD-05） | 採用するAIサービスの応答特性に基づいて決める | DSG-TBD-04の決定後 |

## 7. 採用理由

1. UIモック資産を最大限活用できる。React 19 + Vite 7 + 独自CSSを継承することで、画面実装はモックからの移植を中心に進められる。
2. Javaで業務ロジックを書く目的に合っている。EVM、履歴、集計をSpring BootのService層で堅実に実装できる。
3. 将来のFlutter対応をAPI層で担保できる。OpenAPI定義とJWT寄りの認証方針により、Webフロントエンドの構成へ依存させない。
4. 主要な選択が可逆である。リポジトリ分割、PostgreSQLのバージョンアップ、認証方式の切り替えはいずれも後から再検討できる。
