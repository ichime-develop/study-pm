## 2. 総評

要件定義書は、最終MVPの機能範囲を維持しながら、MVP 1からMVP 4までの段階リリースとして再構成した。

初回レビューで指摘したWBSの入力・階層変更・削除、プロジェクト状態・アーカイブ、過去時点EVM、認証、AI回答、一覧表示、非機能要件の主要論点は要件として確定した。技術スタック、AIサービス、タイムアウト値、未保存変更確認など、実装方式に依存する事項は基本設計へ移管した。

## 3. 対応状況の定義

| 対応状況 | 意味 |
| --- | --- |
| 解消済み | 要件定義書へルールを反映し、基本設計の前提として確定した |
| 基本設計へ移管 | 要件ではなく、方式設計として基本設計で決定する |
| 継続課題 | 要件として未確定であり、基本設計前に判断が必要 |

## 5. ブラッシュアップで確定した主要事項

### 5.1 MVP構成

- 最終MVPの対象範囲は維持する。
- 開発と受入確認をMVP 1からMVP 4へ分割する。
- 認証と計画・実績管理を先に完成させ、その後にEVM、質問管理、AI回答、AI学習計画生成を追加する。

### 5.2 プロジェクトとWBS

- プロジェクト状態とアーカイブを別に管理する。
- 親タスクの計画値と実績値は配下リーフタスクから自動集計する。
- 学習記録が存在するリーフタスクは親タスクへ変更できない。
- WBSの削除、並び替え、階層変更の制約を定義した。

### 5.3 EVMと履歴

- 過去基準日のEVMとバーンダウンを当時の計画で再現する。
- 進捗履歴、WBS計画履歴、プロジェクト期間履歴を保持する。
- PVの日付境界、基準日の時刻境界、表示時の丸め規則を定義した。

### 5.4 質問とAI回答

- 質問はプロジェクト必須、タスク任意とした。
- 解決済みへの変更にはユーザー入力の回答メモを必須とした。
- AI回答は初回同意後に利用し、ユーザーが選択した学習情報だけを送信する。
- AI回答の失敗時に既存データを失わず、再試行できることを定義した。

### 5.5 PC Webと将来のFlutterスマホアプリ

- このリポジトリではPC用Web版を実装対象とする。
- Flutterスマホアプリは別リポジトリ `study-pm-mobile` で作成する想定とする。
- 将来のFlutterスマホアプリからも利用できるよう、認証、データ、入力制約、EVM計算、AI送信範囲、API仕様は共通化を前提にする。
- AI学習計画生成は、PC Web版では画像選択または貼り付けテキストからOCR結果を修正して生成する。

## 7. 継続課題

要件定義として基本設計前に判断が必要な継続課題はない。

基本設計では、要件を満たすために次の点を重点的に検討する。

1. WBS階層変更と履歴保持を両立するデータ構造
2. 過去基準日のEVMとバーンダウンを再現する集計方式
3. アーカイブ済みデータを更新不可にするAPI制御
4. AIへ送信する情報をユーザーが選択・確認できる画面導線
5. 一覧検索と集計を想定件数で実用的に動作させるインデックス
