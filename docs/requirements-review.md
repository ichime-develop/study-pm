# 学習支援Webアプリ 要件定義レビュー

## 1. 文書情報

| 項目 | 内容 |
| --- | --- |
| 対象文書 | `docs/requirements.md` |
| レビュー日 | 2026-06-03 |
| 目的 | 基本設計へ進む前に、要件定義の矛盾、不足、未決事項を整理する |
| 方針 | 実装方式ではなく、ユーザーに提供する振る舞いと業務ルールを先に確定する |

## 2. 総評

現在の要件定義書は、MVPの目的、対象機能、主要な業務ルール、受入条件まで整理されており、初期案として十分な具体性がある。

一方で、WBSの階層変更、削除方針、過去時点のEVM計算など、データ構造や画面操作へ大きく影響する要件が未確定である。基本設計へ進む前に、以下の優先度「高」の論点を確定する必要がある。

## 3. 優先度の定義

| 優先度 | 意味 |
| --- | --- |
| 高 | 基本設計、DB設計、画面設計に直接影響するため、先に確定する |
| 中 | 基本設計中に確定してもよいが、受入条件へ反映する必要がある |
| 低 | 詳細設計または実装方針で確定できる |

## 4. 要件上の矛盾・曖昧さ

| ID | 優先度 | 論点 | 現在の記載 | 確認・修正案 |
| --- | --- | --- | --- | --- |
| REV-01 | 高 | WBSタスクの状態を入力項目に含めるか | WBS-02では状態を設定できるが、9.2では進捗率から自動判定する | 状態はユーザー入力不可とし、進捗率から自動判定する要件へ統一する |
| REV-02 | 高 | 親タスクへ入力できる項目 | 9.3では予定工数、予定日、進捗率は「原則として」リーフタスクに入力するとある | 「原則として」を廃止し、親タスクの予定工数、実績工数、進捗率は入力不可の集計値とするか確定する |
| REV-03 | 高 | 親タスクの予定日の扱い | 親タスクの工数と進捗率の集計は定義されているが、予定日の集計方法がない | 親タスクの開始予定日は配下リーフタスクの最小日、終了予定日は最大日とする案を検討する |
| REV-04 | 高 | リーフタスクを親タスクへ変更する場合 | 親タスクへの学習記録登録は禁止されるが、既存の学習記録や入力済み工数の扱いがない | 学習記録があるタスクには子タスクを追加できない、または記録の移行を必須とする |
| REV-05 | 高 | WBSタスク削除の方式 | WBS-06では削除できるが、子タスクや学習記録がある場合の扱いは確認のみ | 物理削除、論理削除、削除不可のどれにするかを関連データ別に定義する |
| REV-06 | 高 | プロジェクト削除とアーカイブの関係 | PRJ-09では削除時の確認に触れつつ、MVPはアーカイブを基本としている | MVPではプロジェクト削除機能を提供せず、アーカイブと復元のみ提供する案へ統一する |
| REV-07 | 高 | プロジェクト状態の更新方式 | 9.1に状態の用途はあるが、手動更新か自動判定かがない | プロジェクト状態はユーザーが手動更新するか、日付や進捗率から自動判定するかを定義する |
| REV-08 | 高 | 過去時点EVの再現性 | EVM-09では進捗履歴に基づくが、計画変更履歴は定義されていない | 過去時点EVのみ再現するのか、過去時点のBAC・PVも再現するのかを定義する |
| REV-09 | 高 | PV計算の日付境界 | 9.7では開始予定日から終了予定日まで均等配分とあるが、両端を含むか明記されていない | 開始予定日と終了予定日の両方を含む暦日数で均等配分すると明記する |
| REV-10 | 高 | 予定工数が0のタスク | 加重平均、EVM、進捗率計算で0時間タスクの扱いがない | リーフタスクの予定工数を必須かつ0より大きい値とする案を検討する |
| REV-11 | 中 | 進捗率の入力単位 | 0%から100%と10%単位の記載が混在している | MVPでは0、10、20、...、100のみ入力可能と明記する |
| REV-12 | 中 | 質問の関連プロジェクトと関連タスク | 両方設定できるが、異なるプロジェクトのタスクを指定した場合の扱いがない | 関連タスクを指定した場合は、そのタスクが所属するプロジェクトと一致させる |
| REV-13 | 中 | 解決済み質問の再オープン | 解決済みへの変更条件はあるが、未解決へ戻す条件がない | 回答メモを保持したまま未解決または調査中へ戻せるか定義する |
| REV-14 | 中 | ダッシュボードの「今日または直近」 | DSH-06の表示対象期間と件数が曖昧 | 今日を優先し、存在しない場合は未来の直近タスクを指定件数表示するなどのルールを定義する |
| REV-15 | 中 | 「直近の学習記録」の基準 | LOG-08、DSH-04で件数、期間、並び順がない | 学習日降順、同日の場合は更新日時降順などの表示規則を定義する |

## 5. 不足している要件

| ID | 優先度 | 分類 | 不足している内容 | 追加案 |
| --- | --- | --- | --- | --- |
| REV-16 | 高 | 認証 | メールアドレス重複、パスワード要件、ログイン失敗時の扱い | メールアドレスは一意、パスワード最小要件、認証エラー表示を定義する |
| REV-17 | 高 | 認証 | パスワード再設定機能のMVP対象可否 | MVP対象外とする場合も明記する |
| REV-18 | 高 | データ整合性 | プロジェクト期間外の日付をWBSタスクへ設定できるか | タスク予定日はプロジェクト期間内に制限するか、警告のみとするか定義する |
| REV-19 | 高 | データ整合性 | 学習日が未来日の学習記録を許可するか | 学習記録の学習日は当日以前のみ許可する案を検討する |
| REV-20 | 高 | EVM | 進捗履歴の初期値、同日複数更新、基準日の時刻境界 | タスク作成時に0%履歴を作成し、基準日終了時点の最新値を採用する案を検討する |
| REV-21 | 高 | EVM | 計画変更時の扱い | 計画工数や予定日を変更した場合、過去のグラフを現行計画で再計算するか、計画履歴を保持するか定義する |
| REV-22 | 高 | AI回答 | AI APIへ送信する情報の範囲 | 質問タイトル、質問内容、必要最小限の関連情報のみ送信するなどの方針を定義する |
| REV-23 | 高 | AI回答 | AI回答生成中、失敗、再生成時の振る舞い | 二重実行防止、タイムアウト、失敗表示、過去回答保持を要件化する |
| REV-24 | 中 | プロジェクト | アーカイブ済みプロジェクトの復元可否 | 復元可能とするか、アーカイブ後は閲覧のみとするか定義する |
| REV-25 | 中 | WBS | 並び替え可能な範囲 | 同じ親タスク配下のみ並び替え可能とするか、親変更も伴うか定義する |
| REV-26 | 中 | 学習記録 | 親タスクや完了タスクへ記録できるか | リーフタスクのみ登録可能、完了タスクにも追記可能などのルールを定義する |
| REV-27 | 中 | 質問 | 質問と回答の削除方式 | 物理削除か論理削除か、AI回答履歴を含めて定義する |
| REV-28 | 中 | 一覧表示 | ページング、並び順、初期絞り込み | データ件数の想定に合わせ、一覧ごとの初期表示規則を定義する |
| REV-29 | 中 | 非機能 | バックアップの頻度と復旧目標 | 個人開発として現実的な頻度、保持期間、復旧方法を定義する |
| REV-30 | 中 | 非機能 | 対応ブラウザ | PCとスマートフォンの対象ブラウザを定義する |
| REV-31 | 低 | 操作性 | 未保存変更がある画面から離脱する場合の扱い | 確認ダイアログの要否を画面設計で定義する |
| REV-32 | 低 | 監査 | 主要データの変更履歴をどこまで保持するか | MVPでは進捗履歴のみ保持するなど、対象を明記する |

## 6. MVPスコープの見直し候補

現在のMVPには、認証、階層WBS、EVM、バーンダウン、質問管理、AI回答が含まれている。個人開発の初期リリースとしては広いため、完成を優先する場合は段階リリースを検討する。

| リリース | 目的 | 対象機能案 |
| --- | --- | --- |
| MVP 1 | 学習計画と実績を管理できる | 認証、プロジェクト、WBS、学習記録、基本ダッシュボード |
| MVP 2 | 計画との差を可視化できる | 進捗履歴、EVM、バーンダウン、遅延表示 |
| MVP 3 | 学習中の疑問を蓄積できる | 質問管理、回答メモ |
| MVP 4 | AIを学習支援へ利用できる | AI回答生成、再生成、回答履歴 |

段階リリースに分ける場合でも、最終的なMVP対象範囲を変えず、開発と受入確認の単位だけを分割できる。

## 7. 要件定義書へ追加したい章

| 章 | 目的 |
| --- | --- |
| ユースケース | ユーザーがどの順序で何を達成するかを明確にする |
| 入力・表示ルール | 日付、工数、進捗率、文字数、必須項目の共通ルールをまとめる |
| データ整合性ルール | プロジェクト、WBS、学習記録、質問の関連制約をまとめる |
| エラー・例外時の振る舞い | 入力エラー、認証失敗、AI API失敗時にデータを失わないことを定義する |
| MVPリリース分割 | 実装順序ではなく、受入可能な機能単位を定義する |

## 8. 次に確定したい事項

基本設計へ進む前に、以下の順序で要件を確定する。

1. WBSの入力、階層変更、削除ルール
2. プロジェクト状態、アーカイブ、削除ルール
3. EVMと進捗履歴の過去時点再現ルール
4. 学習記録と質問のデータ整合性ルール
5. 認証とAI回答のMVP範囲
6. 一覧表示、ダッシュボード、共通入力ルール
7. 受入条件の具体化

## 9. ドキュメント中心の進行方針

実装へ進む前に、次の成果物を順番に作成する。

1. 要件定義書の確定版
2. 基本設計書
3. 画面一覧、画面遷移図、画面項目定義
4. ER図、テーブル定義
5. REST API一覧、主要API仕様
6. EVM、WBS集計などの業務ロジック設計
7. 必要な機能のみ詳細設計
8. 設計確認用のUIモック

UIモックは、画面設計と操作導線を確認するための成果物として扱い、バックエンド接続や本実装は行わない。
