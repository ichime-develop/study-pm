# 業務ロジック詳細設計

## 1. 目的とスコープ

本書は、学習プロジェクト、WBS、学習記録から導出する業務上の集計値、状態遷移、履歴保存、EVM、バーンダウンの実装前提を定義する。DBの型・制約・外部キーは `database-schema.md`、HTTPのJSON形式とステータスコードはAPI詳細設計で定義する。

対象APIは、`API-PJ-01`、`API-PJ-02`、`API-PJ-05`、`API-PJ-06`、`API-PJ-07`、`API-PJ-08`、`API-WB-01`、`API-WB-02`、`API-WB-04`〜`06`、`API-WB-07`、`API-SL-02`〜`05`、`API-AN-01`〜`03` とする。

- MVP1: 基礎集計、状態遷移、履歴保存、学習サマリー
- MVP2: EVM、バーンダウン、計画不整合警告
- 対象外: SQL実装、APIのJSON形式、集計値の永続化、AI計画生成

## 2. 共通前提

### 2.1 基準日と計算対象

基準日は、注記がない限りアプリケーションの `Clock` から取得したJSTの `LocalDate` とする。利用者が基準日を指定する機能は提供しない。

現行のプロジェクト集計、EVM、バーンダウンでは、対象プロジェクトに属する `task_type = LEAF` の現存タスクだけを計算対象とする。PARENT、削除済みタスク、および削除済みタスクの履歴は対象外とする。

アーカイブ済みプロジェクトの集計取得は許可するが、更新系操作は拒否する。アーカイブは集計値やプロジェクト状態を変更しない。

### 2.2 数値と表示

工数、PV、EV、AC、SV、CV、残予定工数は `BigDecimal` で計算する。計算途中で丸めず、画面・APIの表示用に変換する最後の段階で丸める。

| 値 | 表示ルール |
| --- | --- |
| プロジェクト進捗率 | 小数第1位で四捨五入 |
| 工数、BAC、PV、EV、AC、SV、CV、残予定工数 | 小数第2位で四捨五入し、不要な末尾0を省略 |
| SPI、CPI、差分日数 | 小数第2位で四捨五入 |
| 算出不可 | 数値の代わりに `-` を表示 |

`0` は計算結果、`-` は必要な入力が不足しているため計算できない状態を表す。両者を同一視しない。

### 2.3 算出不可理由

集約APIは、算出不可の指標に理由を付与できるようにする。JSONの項目名はAPI詳細設計で決めるが、業務上の理由は次に限定する。

| 理由 | 対象 |
| --- | --- |
| `NO_LEAF_TASKS` | 計算対象LEAFが0件 |
| `MISSING_SCHEDULE` | 予定開始日または予定終了日が未設定のLEAFが存在する |
| `ZERO_PLANNED_HOURS` | BACまたはPVが0で比率・差分日数を計算できない |
| `ZERO_ACTUAL_HOURS` | ACが0でCPIを計算できない |

### 2.4 進捗履歴の時点判定

日別EVでタスクの対象日 `d` の進捗率を求めるときは、同タスクの `wbs_task_progress_history` から `changed_at` が `d` のJST終端以前である行を選ぶ。候補のうち `changed_at` が最も新しい行を採用し、同一時刻なら `id` の降順で決定的に選ぶ。候補がない場合の進捗率は0%とする。

UUIDの `id` 降順は保存順を表すものではなく、同一時刻の結果を安定させるための決定的なタイブレークに過ぎない。通常は1更新操作を1トランザクションで保存するため、同一時刻の競合は例外的なケースとして扱う。

進捗更新は1回の更新操作を1トランザクションで保存する。これにより、現在値と追加される履歴の整合性を保つ。

## 3. 基礎集計とWBS判定（MVP1）

### 3.1 集計式

| 値 | 式 | LEAFが0件の場合 |
| --- | --- | --- |
| タスク実績工数 | 対象 `wbs_task_id` の `study_logs.study_hours` 合計 | 0h |
| プロジェクト予定工数 | `sum(planned_hours)` | `-` |
| プロジェクト実績工数 | プロジェクトの `study_logs.study_hours` 合計 | 0h |
| プロジェクト進捗率 | `sum(planned_hours * progress_rate) / sum(planned_hours)` | `-` |
| EV | `sum(planned_hours * progress_rate / 100)` | 0h |
| 残予定工数 | `max(0, BAC - EV)` | `-` |

プロジェクト進捗率とEVは同じ重み付き進捗を利用する。LEAFの予定工数は必須で正の値のため、LEAFが1件以上あれば分母は0にならない。

### 3.2 タスク状態と遅延

| 判定 | 条件 |
| --- | --- |
| 未着手 | `progress_rate = 0` |
| 進行中 | `10 <= progress_rate <= 90` |
| 完了 | `progress_rate = 100` |
| 遅延 | `baseDate > planned_end_date` かつ `progress_rate < 100` |

`planned_end_date` が未設定のLEAFは遅延判定の対象外とする。PARENTは状態・進捗率・遅延を持たない。

未完了タスクは、遅延を先頭に置き、残りを終了予定日の昇順で並べる。終了予定日が未設定のタスクは設定済みタスクの後ろに置き、同一条件では `created_at` 昇順、次に `id` 昇順で安定化する。

### 3.3 WBS表示順と計画不整合

WBSの並びは業務ルール10.3に従う。親なしLEAFは開始予定日、終了予定日、作成日時の順に評価する。PARENTは配下LEAFの最小開始予定日、最小終了予定日、PARENT自身の作成日時の順に評価し、配下LEAFは同じ親の中で同じ規則を使う。

計画不整合は、LEAFの予定開始日がプロジェクト開始日より前、または予定終了日がプロジェクト目標終了日より後の場合に警告する。予定開始日・終了日の大小関係は保存前の入力検証で拒否するため、警告として扱わない。予定日未設定は計画不整合ではないが、PVとバーンダウンを算出不可にする。

計画不整合があるLEAFも、BAC、PV、EV、ACの計算対象から除外しない。

### 3.4 プロジェクト一覧の進捗率ソート

`API-PJ-01` で進捗率ソートを選んだ場合は、フィルタ済みの全候補プロジェクトに対して進捗率を計算し、進捗率でソートした後にページングする。DBに集計値は保存しない。進捗率未算出のプロジェクトは昇順・降順とも最後に置き、同値は `updated_at` 降順、次に `id` 昇順で安定化する。

## 4. プロジェクト状態遷移と更新制御（MVP1）

### 4.1 状態遷移

プロジェクト作成時の状態は `NOT_STARTED` とする。ユーザーは `NOT_STARTED`、`IN_PROGRESS`、`COMPLETED` を更新できるが、`COMPLETED` への変更だけは次を満たす必要がある。

1. 対象プロジェクトにLEAFが1件以上ある。
2. 全LEAFの `progress_rate` が100である。

完了済みプロジェクトのLEAFを100未満へ更新した場合は、進捗更新と同じトランザクションでプロジェクト状態を `IN_PROGRESS` へ変更する。`NOT_STARTED` へは自動変更しない。

### 4.2 アーカイブと更新拒否

アーカイブは `archived_at` を設定し、復元は `archived_at` をNULLに戻す。いずれも `status` を変更しない。

アーカイブ済みプロジェクトに対するプロジェクト更新、WBS作成・更新・進捗更新・削除、学習記録の追加・更新・削除は拒否する。集計・履歴・読み取りは許可する。

### 4.3 更新処理の共通順序

更新系処理は原則として次の順序で実行する。

1. 認証済みアカウントによる所有者確認とアーカイブ状態確認
2. 入力値、関連プロジェクト、WBS階層の検証
3. 現在値と入力値の比較
4. 業務データの更新または削除
5. 条件を満たす履歴の追加、必要なプロジェクト状態の自動更新
6. 保存後の集計を取得して応答に使用

学習記録の更新では、更新前と更新後の所属プロジェクト・タスクが異なり得るため、両方のプロジェクトの集計を再取得できる状態にする。ただし、同一プロジェクト外のLEAFへの付け替えはAPI入力で許可しない。

## 5. 履歴保存と更新連動（MVP1）

### 5.1 追加条件

| 操作 | 更新対象 | 履歴の扱い |
| --- | --- | --- |
| プロジェクト新規作成 | `projects` | 期間履歴を追加しない |
| プロジェクト期間変更 | `projects` | 開始日または目標終了日が変わった場合だけ `project_period_history` を1行追加 |
| PARENT作成 | `wbs_tasks` | 計画・進捗履歴を追加しない |
| LEAF作成 | `wbs_tasks` | `progress_rate = 0` とし、初期進捗履歴を1行追加 |
| LEAFの名称・説明変更 | `wbs_tasks` | 計画・進捗履歴を追加しない |
| LEAFの親・予定日・予定工数変更 | `wbs_tasks` | 保存前後の計画値が異なる場合だけ `wbs_task_plan_history` を1行追加 |
| LEAFの進捗率変更 | `wbs_tasks` | 保存前後の進捗率が異なる場合だけ `wbs_task_progress_history` を1行追加 |

計画履歴と進捗履歴には、対象LEAFの `project_id` と `task_name_snapshot` を保存する。履歴の `wbs_task_id` はタスク削除後にNULLとなり得るため、現行集計に利用しない。

### 5.2 同値更新と削除

進捗率が同じ値の場合、LEAFの現在値を更新せず、進捗履歴も追加しない。計画値がすべて同値の場合も計画履歴を追加しない。

LEAFは学習記録が存在する場合に削除できない。PARENTは、配下に学習記録を持つLEAFが1件でもある場合に削除できない。削除可能なPARENTを削除する場合は、配下LEAFを先に削除し、その後PARENTを削除する。削除後も履歴は変更追跡のため残すが、EVM・バーンダウン・現行WBS集計には含めない。

### 5.3 学習記録の更新連動

学習記録の追加、更新、削除後は、実績工数、総学習時間、連続学習日数、AC、CV、CPIを保存せず、現在の `study_logs` から再計算する。MVP1では過去日の学習記録を期限なく編集・削除できる。未来日の登録・更新はJST基準日との比較で拒否する。

完了済みLEAFにも学習記録を追加できる。学習記録の追加・更新・削除は進捗率やプロジェクト状態を自動変更しない。

## 6. 学習サマリー（MVP1）

### 6.1 学習時間

| 値 | 対象 |
| --- | --- |
| 総学習時間 | アカウントに属する全 `study_logs.study_hours` の合計 |
| プロジェクト学習時間 | 対象プロジェクトに属する `study_logs.study_hours` の合計 |

アーカイブ済みプロジェクトの学習記録も、アカウント単位の総学習時間に含める。

### 6.2 連続学習日数

連続学習日数は、対象範囲の `study_date` を重複排除した日集合から求める。アカウント単位では全プロジェクト、プロジェクト単位では対象プロジェクトだけを対象にする。

```text
if today is in studyDates:
    anchor = today
else if yesterday is in studyDates:
    anchor = yesterday
else:
    return 0

count = 0
while anchor - count days is in studyDates:
    count += 1
return count
```

同日に複数の学習記録があっても、連続日数は1日として数える。過去日記録の追加、更新、削除後も、現在の学習日集合で再計算する。

## 7. EVM（MVP2）

### 7.1 入力と計算式

EVMはJST基準日 `D` に対して算出する。計画変更履歴、プロジェクト期間履歴は使わず、現在の `wbs_tasks` と `projects` を計画値として使う。

| 指標 | 式 |
| --- | --- |
| BAC | `sum(LEAF.planned_hours)` |
| PV | 各LEAFの基準日までの日割り計画工数の合計 |
| EV | `sum(LEAF.planned_hours * LEAF.progress_rate / 100)` |
| AC | `sum(study_logs.study_hours where study_date <= D)` |
| SV | `EV - PV` |
| CV | `EV - AC` |
| SPI | `EV / PV` |
| CPI | `EV / AC` |

PVのLEAFごとの寄与は次の通りとする。予定開始日を `S`、予定終了日を `E`、予定工数を `H` とし、日数は両端を含む。

```text
if D < S: 0
else if D >= E: H
else: H * (D - S + 1) / (E - S + 1)
```

`S = E` の場合、`D < S` なら0、それ以外は `H` とする。各LEAFの計算値は丸めずに合計し、表示時だけ丸める。

### 7.2 日別EV

日別EVは、各対象日 `d` について、2.4の履歴時点判定で得た進捗率を使い、現在の `planned_hours` を掛けて求める。

```text
dailyEV(d) = sum(current planned_hours * progressRateAtEndOfDay(d) / 100)
```

タスクの予定工数や予定日を後から変更した場合も、過去の計画履歴を参照せず、現在の予定工数で全対象日を再計算する。削除済みタスクは日別EVに含めない。

### 7.3 指標別の算出可否

| 条件 | BAC | PV | EV | AC | SV | CV | SPI | CPI |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| LEAFが0件 | 0 | 0 | 0 | 0 | 0 | 0 | `-` | `-` |
| 予定日未設定LEAFあり | 算出 | `-` | 算出 | 算出 | `-` | 算出 | `-` | ACが0なら`-`、それ以外は算出 |
| PVが0 | 算出 | 0 | 算出 | 算出 | 算出 | 算出 | `-` | ACに従う |
| ACが0 | 算出 | 算出可能なら算出 | 算出 | 0 | 算出可能なら算出 | EV | PVに従う | `-` |

この表はEVM集約APIが返す原指標の算出方針であり、空プロジェクトの概要画面における表示方針とは区別する。概要画面では、SCR.PJ03-28および3.1に従い、LEAFが0件の場合の予定工数・進捗率・残予定工数を `-`、実績工数を `0h` とする。一方、EVM原指標はbusiness-rules.md 10.8の「値が0の場合も0として表示できる」に従い、BAC/PV/EV/AC/SV/CVを `0`、SPI/CPIを `-` とする。この差は要件間の未解消事項である。

SPIが1未満の場合だけ「遅れ」、CPIが1未満の場合だけ「超過」を表示する。SPI・CPIが1以上の場合は状態ラベルを表示しない。SV・CVは符号付き工数だけを表示する。

## 8. バーンダウンと計画不整合（MVP2）

### 8.1 表示点

バーンダウンの横軸はプロジェクト開始日から目標終了日までの日付、縦軸は残予定工数とする。理想線は全期間、実績線はプロジェクト開始日からJST基準日までの点だけを返す。未来日の実績を仮定しない。

対象日の実績残は `max(0, BAC - dailyEV(d))` とする。基準日時点の実績残は `max(0, BAC - EV)` とする。

プロジェクト期間が1日の場合、理想線はその日の終了時点の0を唯一の点とする。開始前のBACは画面上の別の初期点としては返さない。

### 8.2 差分

バーンダウンの基準日時点では、理想残、実績残、差分工数、差分日数を求める。

```text
idealRemaining = BAC - PV
actualRemaining = max(0, BAC - EV)
workDifference = actualRemaining - idealRemaining
dailyPlannedWork = BAC / inclusiveDays(project.start_date, project.target_end_date)
dayDifference = workDifference / dailyPlannedWork
```

`dailyPlannedWork` が0の場合、差分日数は算出不可とする。差分日数の正負はそのまま表示し、前倒し・予定どおり・遅れの閾値ラベルは付けない。

### 8.3 算出不可

バーンダウン全体は、LEAFが0件、BACが0、または予定日未設定LEAFが1件でもある場合に算出不可とする。計画不整合のLEAFは算出対象に含め、警告として別途返す。

### 8.4 要件間の未解決事項

業務ルール10.9には「理想線はプロジェクト開始日のBACから目標終了日の0まで直線」とある一方、同じ節では理想残を `BAC - PV` としている。PVは業務ルール10.8によりタスクごとの予定期間で日割りされるため、タスクの予定が偏っている場合は直線にならない。

本書では差分工数・差分日数を業務ルールどおり `BAC - PV` で算出する。チャートの理想線を直線にするか、`BAC - PV` の計画消化線にするかは、MVP2実装前に要件として決定する必要がある。既存要件・基本設計は本書作成時点では変更しない。
