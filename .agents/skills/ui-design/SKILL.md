# UI Design Skill

## Purpose

PC Web版 `study-pm` のUIモックを作成・修正・レビューするときに、UI原則、画面間整合性、要件定義との差分をまとめて扱う。

## Product Direction

- 対象は、学習計画と実績を定量管理したいエンジニア。
- トーンは、静か、実務的、情報密度高め、迷わない、繰り返し使いやすい。
- 近いカテゴリは、Tech/SaaS、B2B SaaS dashboard、Data-dense dashboard、Minimalism/Swiss style。
- 画面はランディングページではなく、日常的に使う業務ツールとして設計する。
- 装飾より、予定、実績、進捗、遅延、質問、AI支援の判断が速いことを優先する。

## Workflow

### 1. 変更意図を整理する

- ユーザー要望を、画面変更、導線変更、文言変更、データ変更、要件変更候補に分ける。
- 要件レベルの変更か、基本設計・画面設計レベルの変更かを分ける。
- ユーザーが実装を依頼している場合は、提案だけで止めずにmockを修正する。

### 2. 影響範囲を検索する

変更前に `rg` で以下を確認する。

- 対象画面名、ボタン文言、サイドバー項目、画面切り替え項目
- 変更する業務用語と同義語
- 遷移先、screen id、enum、固定データ
- 関連するCSS class、コンポーネント、データ定義
- `docs/requirements/` 内の同じ概念

画面削除や名称変更では、最低限以下を確認する。

```text
mock/src
docs/requirements
```

### 3. 既存UIパターンへ寄せる

- 既存のコンポーネント、CSS class、余白、フォントサイズ、カード、ボタン、フォーム、表、ポップオーバーのパターンを先に確認する。
- 新しい見た目を作る前に、既存パターンを再利用できるか判断する。
- 一時的な個別CSSを増やす場合は、同種UIへ広げるべきか確認する。
- 同じ意味の情報は、画面間で同じ名称、表示順、単位、入力方法に揃える。
- テーブル、詳細パネル、モーダル、ポップオーバーは、既存の密度と操作感に合わせる。
- 詳細パネル、モーダル、ポップオーバーは、明示的な閉じる操作に加えて、欄外クリックで閉じられるかを検討する。入力欄、セレクト、ボタンなど内部操作では閉じないようにする。
- 未保存の入力が失われる可能性がある場合は、欄外クリックで即時に閉じるか、未保存変更確認を出すかを基本設計で明確にする。

## UI Principles

### Layout

- PC Webを主対象にし、まず `1280px` 幅で主要操作が破綻しないことを下限目安にする。
- 大画面では読みやすい最大幅を保ち、小さいPCでは余白を削って折り返す。
- ガントチャートのような横長データは横スクロールを許容する。
- ダッシュボード、進捗分析、フォーム、一覧は横スクロールに頼らず、グリッドを折り返す。
- サイドバーがメイン領域を圧迫するため、不要な左右余白を増やさない。
- 画面上部の説明文は最小限にする。画面名、指標、ラベル、ヘルプで意図が伝わる場合は説明文を置かない。
- 重要な情報は初期表示で見える位置に置くが、カードを増やしすぎない。

### Components

- ボタンは、主要操作を1つに絞り、補助操作は控えめにする。
- アイコンだけのボタンには、必ず意味が分かるラベルまたはアクセシブル名を用意する。
- 指標カードは、ラベル、値、必要なヘルプだけで構成し、説明文をカード内に増やさない。
- 表は、情報密度を高めつつ、列幅、固定列、sticky header、横スクロールの役割を明確にする。
- 詳細パネルは、選択中の対象を編集・補足する場所とし、独立画面と役割を重複させない。
- 詳細パネルは、パネル外のクリックで閉じられる場合でも、パネル内の入力操作や保存操作を妨げない。
- ヘルプ表示は、SVの `?` パターンを基準にし、説明、計算式、値の見方を短く並べる。

### Typography And Spacing

- 見出しは画面階層に合わせて控えめにする。業務ツール内で過度なheroサイズを使わない。
- 文字サイズはviewport幅で拡大縮小しない。
- 数値は読みやすさを優先し、桁や単位が揃うようにする。
- 余白は「区切るため」に使い、「見た目を広げるため」だけに増やさない。
- カード内の余白、表の行高、フォームの入力サイズは画面間で揃える。
- 小さいPCで情報が詰まる場合は、余白を増やすのではなく、列数を減らして折り返す。

### Color And Visual Style

- ベースは白、薄いグレー、落ち着いた青を中心にする。
- 強調色は、主要操作、選択状態、警告、危険状態に限定する。
- 紫や青紫のグラデーション、派手な装飾、AIっぽい抽象背景は避ける。
- 進捗、警告、危険、完了の色は意味を固定する。
- コントラストは通常テキストで読みやすい水準を保つ。
- シャドウや角丸は控えめにし、カードが過剰に浮いた印象にならないようにする。

### Accessibility

- クリック可能な要素は見た目とカーソルで操作可能だと分かるようにする。
- キーボードフォーカスが見える状態を保つ。
- ポップオーバーやヘルプは、hoverだけでなくfocusでも表示できるようにする。
- フォーム項目にはラベルを対応させる。
- 色だけで状態を伝えない。テキスト、値、ラベル、境界線なども併用する。
- アニメーションを追加する場合は控えめにし、レイアウトを揺らすアニメーションを避ける。

### Responsive Rules

- `1440px` 以上: 標準のPC表示。横並びを活かしてよい。
- `1280px` から `1439px`: 余白を少し詰め、進捗分析のような横並びは必要に応じて段組みを変える。
- `1024px` から `1279px`: サマリカードは2列、EVM指標は2列、チャートは全幅を基本にする。
- `1024px` 未満: PC正式対応外または簡易表示として扱い、必要になった時点で別途方針を決める。
- WBS・ガントは横スクロールでよい。その他の画面は折り返しを優先する。

## Required Checks

修正後に以下を確認する。

- サイドバー、画面切り替え、ヘッダー、ボタンに古い導線が残っていないか。
- 削除した画面や機能へ遷移するボタンが残っていないか。
- 同じ概念が複数の名前で表示されていないか。
- 主要指標、表、詳細パネル、フォームの表示順と単位が揃っているか。
- 画面上部、カード、表、サイドパネルの余白と文字サイズが既存画面と合っているか。
- ダミーデータ追加や固定データ変更により、集計値、進捗率、EVM、バッジ表示が不自然になっていないか。
- 縦横スクロール、sticky header、固定列が想定どおり機能するか。
- `1280px` 幅で主要画面が横に切れないか。
- hover/focus状態、ヘルプ、フォームラベル、アクセシブル名が不足していないか。

## Requirements Alignment

mock変更後、関連する `docs/requirements/summary/README.md` と `docs/requirements/details/` を確認する。

- mockが要件とズレた場合、ズレを明記する。
- mockが正の場合、要件修正候補を出す。
- 要件へ入れる内容と、基本設計・画面設計へ送る内容を分ける。
- 画面部品、表示位置、フォント、列幅、具体的なUI操作は原則として要件に入れない。
- 業務上の能力、制約、入力できる情報、集計の意味は要件に残す。
- 要件ファイルを修正する場合は、`requirements` Skillの方針も併用する。

## Anti-Patterns

- 説明文を各所に置きすぎる。
- カードの中にカードを重ねる。
- 画面ごとにフォントサイズ、余白、ボタン形状、表密度を変える。
- 大画面の見た目だけで横並びを固定する。
- 要件レベルの内容を、列幅、表示位置、フォントなどの画面設計レベルで書く。
- ランディングページ風のhero、装飾的なグラデーション、派手な影を業務画面に入れる。
- 見た目のために余白を増やし、小さいPCで主要情報を圧迫する。

## Validation

- mock実装を変更した場合は、原則として `mock` ディレクトリでビルドを実行する。
- フロントエンドの見た目・操作に関わる変更は、可能な範囲でブラウザ表示も確認する。
- 検証できなかった場合は、理由と残リスクを明記する。

## Output Format

- 変更したUI
- 横断確認した範囲
- 要件との差分
- 要件へ反映すべき内容
- 基本設計へ送る内容
- 検証結果
- 残るリスク
